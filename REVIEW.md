# REVIEW.md

I read the starter `app/main.py` line by line and tested the helper functions with awkward inputs
(time zones, overnight shifts, exact boundary times like 09:40:01). These are the 15 most important
defects I found, with what is wrong, how I noticed it, and how I fixed it.
Line numbers refer to the original starter file.

| # | Where (function / line) | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes`, lines 36-37 | It changes the time into whole minutes first and only then checks `> 10`. So 10 minutes 1 second becomes `10`, and `10 > 10` is false. | Punch in at 09:40:01 on a 09:30 shift. The rule says 10, but the starter returns 0. | I compare in seconds (`> 600`) and divide by 60 only after that. |
| 2 | `compute_late_minutes`, line 35 | The shift start is built in the same time zone as the punch-in. A punch-in sent in UTC is compared with 09:30 UTC instead of 09:30 IST, so the answer is wrong by 5 hours 30 minutes. | Send 09:41:01 IST written as 04:11:01 UTC. It should give 11, the starter gives 0. | I convert every time to IST first and build the shift start in IST. |
| 3 | `compute_late_minutes` line 35 and `compute_overtime` line 46 | Both functions put the shift on the punch-in's own date. For an overnight shift (22:00 to 06:00), the shift ends the next morning, and a punch-in at 05:30 belongs to the previous day. | Shift 22:00 to 06:00, punch out at 06:40 next day. Overtime should be 40, the starter gives a wrong number. | A new function `shift_window` works out the right date, shift start and shift end (the end is on the next day for overnight shifts). |
| 4 | `compute_work_hours`, line 41 | Python `round()` is not "half up". It works on floating-point numbers, so `round(2.675, 2)` gives 2.67. The rule wants half up. | A work time that ends exactly on a half, such as 4 hours 29 minutes 42 seconds = 4.495 hours. | I use `Decimal` with `ROUND_HALF_UP`. |
| 5 | `compute_overtime`, lines 44-47 | There is no 30-minute minimum. The rule says overtime counts only if it is at least 30 minutes. | Leave 10 minutes after shift end. It should give 0 overtime, but the starter gives 10. | It returns the minutes only if they are 30 or more, otherwise 0. |
| 6 | `punch_in`, lines 104-118 | It checks whether a record exists and then inserts. Two identical punch-ins at the same moment can both pass the check, so one employee gets two records for one day. | Send two identical punch-in requests at the same time. Both can return 201. | A unique index on `(emp_code, date)`. I insert directly and turn `DuplicateKeyError` into 409. The database lets only one win. (`create_employee` had the same problem and the same fix.) |
| 7 | `punch_in`, lines 101 and 113 | If the employee does not exist, `emp` is `None` and `emp["shift_start"]` crashes. The user gets a 500 error instead of a clear message. | Punch in with an unknown `emp_code`. | It returns 404 when the employee is not found. |
| 8 | `list_attendance`, lines 144-147 | It loads every matching record into Python memory, sorts them in Python, and then cuts one page. This is slow with 100,000 records and uses a lot of memory. | Fill the collection with a lot of records and call `GET /attendance`. | MongoDB does the sort, skip and limit, supported by an index. The total comes from `count_documents`. |
| 9 | `list_employees`, lines 93-94 | `skip = page * page_size` skips the first page of results. And `total` counts all employees, ignoring the department filter. | Call page 1 with page_size 2: you do not get the first two employees. Filter by department: `total` is too big. | `skip = (page - 1) * page_size`, and `total` uses the same filter as the list. |
| 10 | `punch_in` lines 119-121 and `list_attendance` line 149 | The response contains an `id` (the MongoDB `_id`) and raw dates. The contract forbids `_id` and wants times as epoch milliseconds (numbers). | Look at any attendance response: it has an `id` field and date strings. | A function `record_out` builds the response from known fields only and converts times to epoch milliseconds. |
| 11 | `EmployeeIn`, lines 53-60 | There is no validation. Any text is accepted for `emp_code`, `email` and `joined_on` (even the word "string"), and a shift can start and end at the same time. | Post `joined_on: "string"` and it is saved with status 201. | Pydantic rules: `EMP` plus 4-6 digits, an email pattern, a real calendar date, `HH:MM` times, and `shift_start` must differ from `shift_end`. Bad input gives 422. |
| 12 | `PunchInIn` lines 65-66 and `punch_in` line 102 | `status` accepts any text, any integer is accepted for `punched_at` (even seconds instead of milliseconds), and `if body.punched_at` treats 0 as "not given". | Send `status: "banana"`, or a `punched_at` in seconds. Both are saved. | `status` is limited to PRESENT, WFH or ON_DUTY. `punched_at` must be a whole number of milliseconds in a sensible range, and I check `is not None`. Otherwise 422. |
| 13 | `punch_in`, lines 102-103 | It uses the server's own clock and the server's own date (`datetime.now()`). The attendance date must be the date in IST, and the server may run in another time zone. | On a server set to UTC, a punch-in at 02:00 IST gets the previous day's date. | Times are handled in UTC, and the date comes from `shift_window`, which uses IST. |
| 14 | `health`, line 74 | It always says "ok", even when MongoDB is down. | Stop the database and call `/health`: it still says ok. | It pings MongoDB and returns 503 if the database cannot be reached. |
| 15 | whole file | There are no indexes at all. The unique guarantees in #6 and the list and analytics queries need them. | Run explain on the list query: it scans the whole collection. | `create_indexes()` runs at startup and is safe to run again. See DECISIONS.md for the list. |

## Things I looked at and decided were NOT defects

- **`IST = timezone(timedelta(hours=5, minutes=30))` (line 25)** is correct. India has no daylight saving time, so a fixed +05:30 offset is right.
- **Keeping `date` as text like `"2026-07-06"`** and comparing it with `$gte` / `$lte` is fine, because ISO dates sort in the same order as real dates.
- **Returning 409 for a duplicate employee** is the correct status code. Only the way it was checked was weak (see #6).
